## 2026-09-08T11:28Z / #0 / gates — 自己検証

- **結果**: このリポジトリに npm のテスト基盤は無いため、G1 相当はシェルの構文検査と手動シナリオで代替した
- **見つけた不具合と修正**:
  1. `die` を `$(...)` の中で呼んでも親シェルは死なない。Vault 未接続で `flush` した際、
     エラーを出したまま `rm` まで到達して**内部ジャーナルを削除した**（データ損失）。
     → Vault の判定を親シェルに出し、Vault への着地を `grep` で確認するまで削除しない構造に変更
  2. 全角括弧の直前の `$vf` を bash が変数名の一部として解釈し `unbound variable` で落ちた。
     → 多バイト文字に隣接する変数展開を全て `${var}` に修正
- **なぜ 1 が起きたか**: 「検証関数の中で die すれば安全」という前提が、コマンド置換では成立しないため

## 2026-09-08T11:53Z / #3 / gates — G4 レビュー差し戻し対応

- **結果**: `sub-agent-evaluator` による独立レビューで ❌ 差し戻し。重要度「高」2件・「中」3件・「低」3件
- **落ちた内容**:
  - [高] エピック slug が無検証。`../` を含む slug でジャーナルディレクトリ外の任意ファイルに追記できた
  - [高] 上記と `cmd_flush` の `rm -f` が組み合わさり、任意ファイルを削除できた（レビュアーが README.md の削除を再現）
  - [中] スラッシュ入り slug でヒアドキュメントのリダイレクトが失敗しても「作成した」と成功報告していた
  - [中] flush の着地確認が `grep -qF "$header"` だけで、同一見出しが既にあると誤爆する
  - [中] `LOOP_PROJECT_NAME` も無検証で Vault の `projects/` 外にファイルを作れた
- **なぜ見落としたか**: 自分のテストは「正常系」と「Vault 未接続」に閉じていて、
  **slug を敵性入力として扱っていなかった**。悪意ある入力どころか、`epic/search/filter` のような
  自然なネストブランチ名でも壊れる経路だった
- **差し戻し先**: 実装（Coder 相当）。設計ではなく入力検証の欠落なので Architect には戻さない
- **対処**:
  - `valid_slug` / `require_slug` / `require_safe_name` / `assert_in_journal_dir` を追加。検証は必ず親シェルで実行
  - ブランチ由来の slug は `tr '/' '-'` で潰す（`worktree.sh` と同じ規約に揃えた）
  - `rm` の直前で `assert_in_journal_dir` を再実行する多層防御
  - flush の着地確認を「見出しの存在」から「追記行数の実測 + 末尾 N 行に見出しがあること」に変更
  - `cmd_start` にリダイレクト失敗の検知を追加、重複 flush に警告を追加
- **再検証**: レビュアーの再現手順を全てそのまま実行し、全件が拒否されることを確認。正常系も回帰確認済み
