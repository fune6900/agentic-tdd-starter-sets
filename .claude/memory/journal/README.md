# インナーループ・ジャーナル（内部バッファ）

**このディレクトリは、外部記憶（Obsidian Vault）へ書き写す前の一時バッファだ。**

インナーループの節目ごとの記録が `<epic-slug>.md` に貯まり、
アウターループ完了時に Vault の `projects/<project>.md` へ丸ごと書き写されて**削除される**。

```
インナーループの節目 ──→ .claude/memory/journal/<epic-slug>.md   （Git 管理・一時）
                                    │
                     アウターループ完了 flush
                                    ↓
                        <VAULT>/projects/<project>.md            （永続・追記のみ）
```

---

## なぜ Git で管理するのか

**別端末・別作業者が続きを引き継ぐため。**
Vault はローカルディスクにしか無い。ジャーナルがリポジトリに乗っていれば、
別のマシンで `git pull` した AI が、前のセッションが何をやってなぜそうしたかを読める。

`loop-state.json`（retry 回数などの実行時状態）とは目的が違う。あれは捨ててよい状態、
ここは引き継ぐべき記録。だから `.gitignore` の扱いが逆になっている。

| ファイル | 中身 | Git |
| --- | --- | --- |
| `<epic-slug>.md` | インナーループの経緯（節目4点） | **コミットする** |
| `.vault` | この端末の Vault パス + 紐付いたプロジェクト名 | しない（端末ごとに違う） |
| `.active` | 進行中のエピック slug | しない（作業者ごとに違う） |
| `.project` | Vault 側のファイル名の上書き（任意） | しない |

### `.vault` はプロジェクトに紐付く

2行構成になっている。

```
/path/to/Obsidian Vault      ← 1行目: Vault のパス
agentic-tdd-starter-sets     ← 2行目: このポインタを作ったプロジェクト名
```

**2行目が現在のプロジェクトの「同一性」と食い違う場合、接続を拒否する。**

紐付けに使うのは**上書きできない値**だ。共通の `.git` を辿って得たリポジトリ名を使う。
`.project` や `LOOP_PROJECT_NAME` で決まる**表示名は使わない**。
表示名で紐付けると、`.project` も `.vault` と同じ経路でコピーされるため、
両方を持ち込まれた時点で照合が無意味になる（実際に回避を再現した）。

| 値 | 決まり方 | 上書き | 用途 |
| --- | --- | --- | --- |
| 同一性 | 共通の `.git` からリポジトリ名 | **不可** | ポインタの紐付け |
| 表示名 | `LOOP_PROJECT_NAME` → `.project` → 同一性 | 可 | Vault のファイル名 |

`.gitignore` 済みなので clone には含まれないが、**作業ツリーごとコピーすると付いてくる**。
そのまま使うと、導入先プロジェクトの記録がテンプレート提供者の Vault へ流れ込む。
Vault はリポジトリ外＝権限設定も `.gitignore` も届かず、多くはクラウド同期される。
追記専用なので後から消しても同期先の履歴に残る。

拒否されたら繋ぎ直す:

```bash
bash .claude/scripts/loop-journal.sh init <vault-path>
```

`LOOP_VAULT_DIR` による明示指定は、持ち主の意図として扱うので常に優先される。

### worktree でも同じプロジェクト名になる

プロジェクト名は共通の `.git` を辿って本体のリポジトリ名から決める。
作業領域のディレクトリ名（＝ブランチ名）は使わない。使うと記録がブランチごとに散る。

## 記録する節目（インナーループ・4点）

| phase | いつ | 何を書くか |
| --- | --- | --- |
| `start` | Issue 着手時 | 何をやるか / 参照した教訓 / 実装方針と**その理由** |
| `impl` | Generator フェーズ完了時 | 何を作ったか / **なぜその設計にしたか** / 捨てた選択肢 |
| `gates` | G1〜G5 を一巡した時点 | ゲート結果 / FAIL の内容 / 差し戻し先と**その判断理由** |
| `done` / `halt` | 完了時 / ハードストップ時 | 結果 / 残課題 / 次の Issue への申し送り |

ゲート1つごとには書かない。**一巡してまとめて1エントリ**。
1回1エントリの粒度を守らないと、読み返せない量になって記憶として機能しなくなる。

```bash
bash .claude/scripts/loop-journal.sh inner 42 impl "記事検索の実装" <<'ENTRY'
- **やったこと**: `searchArticles` Server Action と `SearchResultSchema` を追加
- **なぜ**: 戻り値を Zod から導出しないと `any` に落ちる（lessons.md #42 の教訓）
- **結果**: ユニットテスト12件グリーン
- **次**: G1 へ
ENTRY
```

## 制約

### エピック slug に使える文字

**英数字で始まり、英数字 `.` `_` `-` のみ。** `/` と `..` は拒否される。
slug はそのままファイル名になるため、パスを跨ぐ値を通すとジャーナル以外のファイルを
書き換え・削除しうる。スクリプト側で検証し、違反したら停止する。

ブランチ名 `epic/<slug>` から導出する場合はスラッシュが `-` に潰される（`epic/a/b` → `a-b`）。
`worktree.sh` のブランチ名スラッグ化と同じ規約。

### 並列ワークツリーでの追記

同一エピックの Issue を複数のワークツリーで**並列に**流すと、
各ワークツリーのローカルコピー上で同じ `<epic-slug>.md` に独立して追記が発生し、
マージ時に Git のコンフリクトになる（データ消失ではなく、Git が検知する衝突）。

`epic-flow` は依存順に**1 Issue ずつ**流す設計なので通常は起きない。
意図的に並列化する場合は、エピックを分けるか、コンフリクトの解消を前提に運用する。

## 教訓（lessons.md）との違い

| | ジャーナル | `lessons.md` |
| --- | --- | --- |
| 中身 | **経緯**（何をやって、なぜそうしたか） | **教訓**（次回ルール） |
| 寿命 | エピック完了で Vault へ移して削除 | 永続。リポジトリに残す |
| 読む相手 | 続きをやる次のセッション | 全ての未来のセッション |

「Server Action を Zod で書いた、理由はこう」はジャーナル。
「Server Action の戻り値は必ず Zod スキーマとペアで定義する」は `lessons.md`。
**混ぜるな。** ジャーナルは消えるので、教訓をここに書くと消える。
