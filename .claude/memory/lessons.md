# 教訓ログ（Lessons）

ループが学習するための外部メモリ。セッションを跨いで引き継がれる唯一の資産。

**書き込みは `/loop-retro` 経由。** 手書きで雑に追記しない。
書き方と運用ルールは `@.claude/memory/README.md` を参照。

---

## 使い方（このテンプレを導入したプロジェクトでの初手）

1. 最初の Issue が完了したら `/loop-retro` を実行し、この下に教訓を積む
2. 立案のメイド（Planner）は分解前に必ずこのファイル全体を読む
3. 同じ事象が再発したら、新規追加ではなく既存項目に日付を追記する

## 教訓

### 2026-10-10 / #23 `rm` / `curl` / `chmod` / `wget` は承認待ちになり、背景のエージェントもメインも戻らない
- **事象**: #23 で QA が 3 回、10〜20 分無進捗で止まった（`rm <ファイル>` 単独でも止まった）。続いて Tech Lead 自身の `until curl … ; do sleep 1; done` が 2 時間 23 分戻らず、時間上限（起きていた時間 252 分 / 180 分）でハードストップした。Mac は起きていた
- **原因**: `.claude/settings.json` の `permissions.ask` に `Bash(rm *)` / `Bash(chmod *)` / `Bash(wget *)` / `Bash(curl *)` がある。承認待ちのあいだ、背景のサブエージェントは戻れず、メインもユーザーが応答するまで止まる。#21・#22 の G2 で Tester が止まったのも同じ（curl）と見られる。「複合コマンドだから」「スリープだから」と推測していたのは誤り
- **対処**: エージェントへの指示に「Bash ツールで rm / curl / chmod / wget を直接実行しない。削除は `find <パス> -type f -delete`、HTTP は `node -e` の `fetch`」を入れ、以後止まらなかった。テストスクリプトの中での使用は問題ない（ツールの承認対象は打ったコマンド文字列だけ）
- **次回ルール**: **Bash ツールで直接 `rm` / `curl` / `chmod` / `wget` を打たない（メインもサブエージェントも）。** サブエージェントへの指示には毎回この行を入れる。止まったら、まず最後のコマンドが `ask` に当たっていないかを見る
- **併せて**: `sub-agent-qa` には Edit ツールが無い（Read / Write / Bash）。既存ファイルの部分変更は python の置換スクリプトで行わせ、1 回の Write は 300 行までにする

### 2026-10-10 / #23 監視の既定ポート 4319 は、導入先の別アプリと衝突しうる
- **事象**: G2 で監視サーバを 4319 で起動しようとして失敗。別アプリ（test-todo-board の Docker）が 4 日前から 127.0.0.1:4319 を使っており、監視フックのイベントはそちらへ送られていた（405 で拒否されていた）
- **原因**: フックは宛先のポートが本物の監視サーバかを確かめない（fail open で黙って送る）。ポートが空いている前提で既定値を決めていた
- **対処**: G2 は別ポート（`LOOP_MONITOR_PORT`）の検証サーバで行った。恒久対処はマスター判断待ち
- **次回ルール**: 監視の動作確認の前に `lsof -nP -iTCP:<port> -sTCP:LISTEN` で、そのポートを握っているのが監視サーバかを確かめる

### 2026-10-10 / #22 1 つの検査を守るテストは「他を全部正しく揃えて、その 1 項目だけ壊した入力」で書く
- **事象**: ビューの `formatLoopPanel` の status 許可リスト検査（`Object.hasOwn(LOOP_STATES, status)`）を外す変異が、G1〜G2 を通った後の G3 で生存した。テストの不正入力が `{ status: 'constructor' }` のように status だけを持ち、必須項目の欠落という別の検査で先に unknown になっていた
- **原因**: 不正入力を最小の形で書き、「狙った検査まで到達しているか」を確かめなかった。結果（unknown）が同じなので、どの検査が効いたかがテストからは分からない
- **対処**: `running()` などの正しい入力の上書きで 1 項目だけ壊すテストを足し（`.claude/monitor/test/view-loop.test.mjs` / `loop-state.test.mjs`）、検査を 1 つずつ外した隔離コピーで落ちることを確認
- **次回ルール**: 検証の各条件のテストは、**他の項目をすべて正しくした入力から 1 項目だけ壊して**書く。最小の不正入力は使わない。条件ごとに「その条件だけを外す変異」で落ちることを確かめる

### 2026-10-10 / #22 本物の状態ファイルを既定パスにしたら、テストのヘルパの既定は存在しない一時パスにする
- **事象**: `createServer` の `loopStatePath` の既定をリポジトリの `.claude/memory/loop-state.json` にした結果、既存のサーバテストが開発者の手元の実行中ループの状態を読み、`/api/state` の厳密一致テストが落ちた（手元の状態しだいで結果が変わる）
- **原因**: 本番の既定値（ホストの実ファイル）を足したとき、それを暗黙に使う既存テストの入口（`startServer` / `createWithDataDir` / CLI 起動）を洗い出さなかった
- **対処**: テストのヘルパの既定を存在しない一時パスにし、CLI 起動の子プロセスの env にも同じパスを入れた（`.claude/monitor/test/helpers.mjs`）
- **次回ルール**: 本番コードに「ホストの実ファイルを指す既定値」を足したら、**同じ変更でテストのヘルパ・CLI 起動の既定を存在しない一時パスに倒す**。`grep -rn "createServer("` のように既定値を暗黙に使う入口を全部洗い出す

### 2026-10-10 / #22 指示に書く仕様の値は、仕様ファイルから引用する。記憶で書かない
- **事象**: Tech Lead が QA への指示に「双方向制御文字（U+061C を含む）」と書いた。唯一の正の `event-schema.md` は U+061C を含まず、受信側だけが ALM を含む `file_path` を拒否する実装になりかけた（Coder の報告で発覚して戻した）
- **原因**: 範囲を仕様ファイルで確かめず、Unicode の一般知識から書いた。下流は指示を正として実装・テストするので、指示の誤りがそのまま実装とテストの両方に入る
- **対処**: 共有の文字クラスを仕様どおりに戻し、`event-schema.md` の行から範囲を読んで BMP 全域で突き合わせるテストを追加（`.claude/monitor/test/control-chars.test.mjs`）。ALM の追加は送受信を揃える Issue #35 に切り出した
- **次回ルール**: サブエージェントへの指示に仕様の値（範囲・列挙・上限）を書くときは、**仕様ファイルの該当行を開いて引用する**。仕様と照合するテストがあれば、値は指示ではなく仕様から読ませる

### 2026-10-10 / #32 OS の値を「同一性」の比較に使うなら、実機で時間をあけて 2 回読んでから採用する
- **事象**: macOS の起動 ID に `sysctl -n kern.boottime` の出力全体を使った。単体テスト 95 件・G1 は PASS したが、G2 の実機確認で、同じ起動中にも時刻補正で usec が変わり（53346 → 118052）、init から数分で起動 ID が不一致になって壁時計に倒れることが分かった
- **原因**: 「起動時刻なので起動中は不変」と推測で決め、実機で時間をあけて読み直さなかった。テストは偽の sysctl が固定値を返すため、値の揺れを原理的に検出できない
- **対処**: 起動ごとの UUID である `kern.bootsessionuuid` に変更（`.claude/scripts/loop-state.sh` の `boot_id_now`）。偽 sysctl が `kern.boottime` を呼ぶたびに usec を変える回帰テストを追加（`tests/scripts/loop-state.test.sh`）
- **次回ルール**: OS・環境から取る値を「同じかどうか」の比較キーにするときは、採用前に**実機で数分あけて 2 回以上読み**、揺れないことを確かめる。G2 にも「時間をあけて再判定する」項目を入れる。偽物で固定したテストは値の揺れを検出しない

### 2026-10-08 / #21 Playwright MCP の `.playwright-mcp/` はブラウザを閉じてから消す
- **事象**: G2 の後片付けで `.playwright-mcp/` のログを消しても、ブラウザを開いたままだとログが再生成されて `rmdir` が失敗した。前回の G2 は後片付けとサーバ停止・`gate G2 pass` の記録を 1 コマンドに連結しており、そのコマンドの結果が返らないまま止まった（G2 の記録が残らなかった）
- **原因**: Playwright MCP はブラウザが開いている間コンソール・ページのログを `.playwright-mcp/` に書き続ける。連結コマンドで止まった直接の原因は未確定（同時刻にスリープの可能性）
- **対処**: Tester への指示を「`browser_close` → `kill` → 画像を個別に `rm` → `find .playwright-mcp -type f -delete` と `rmdir` → `git status` → 単独で `loop-state.sh gate`」の順に、各手順を別の呼び出しにした。`rm -r` は使わせない
- **次回ルール**: G2 を委任するときは、後片付けを上の順で 1 手順 1 呼び出しにし、ゲートの記録は最後に単独で実行するよう指示に書く
- **再発**: 2026-10-10 #22（G2 の Tester が検証サーバを `nohup node … > log 2>&1 &` の 1 コマンドで起動しようとして結果が返らず、15 分無進捗。サーバのプロセスもログも無く、コマンドは実行されていなかった（権限確認待ちと推定・未確定）。**検証用サーバは Tech Lead が Bash の run_in_background で起動し、ポートを渡す。ゲート担当には起動・停止をさせず、`&` / `nohup` / 連結を禁止する**と、以後の G2 は止まらなかった）

### 2026-10-05 / #20 除外パターンは「どの階層に効くか」を実物で確かめる。直下に効いても配下には効かない
- **事象**: G5 の低指摘で `.dockerignore` に env 系ファイルの除外を1行足し、静的テスト（行があるか）とスモーク（コンテキスト直下に囮を置いてイメージに入らないか）は PASS した。G2 が `server/` 配下に囮を置いて実ビルドすると、`COPY server ./server` 経由でイメージに入った
- **原因**: `.dockerignore` のパターンはコンテキスト直下を基準に照合され、サブディレクトリには `**/` が要る（Docker の仕様）。テストの囮を直下にしか置いておらず、「除外が効く範囲」を検査していなかった（#19 の「行き先を数える」と同じく、**入口の階層を数えていない**）
- **対処**: 未対処（ハードストップ中）。修正方針は `**/` 付きにして、テストの囮を実際にコピーされる階層（`server/` 配下）にも置く
- **次回ルール**: ignore 系（`.dockerignore`・`.gitignore`・`.npmignore`）に除外を足すときは、**実際に取り込まれる全ての階層に囮を置いて**確かめる。「行がある」ことを検査しても、効いている証明にはならない
- **解決**: 2026-10-07 マスター指示で上限なし再開し、`**/` 付きに加えて許可リスト方式（`*` → `!server` → 秘密パターン）にした。テストの囮は直下・`server/`・深い階層に置く
- **併せて**: G2 の Tester は Write ツールを持たないため、env 系の囮ファイル（Bash ではガードに止められる）を作れず実証できなかった。**Write を持たないゲート担当に env 系の囮が要る検証を頼むときは、Tech Lead が Write で囮入りのコンテキストを scratchpad に用意して渡す**

### 2026-10-04 / #19 Origin 検査は「ブラウザは常に Origin を付ける」前提では塞がらない
- **事象**: ローカル監視サーバに Host 検査と Origin 検査（Origin があれば同一オリジンのみ）を入れ、G1〜G4 は PASS した。G5 で、任意のページに `<img src="http://127.0.0.1:4319/api/stream">` を並べるだけで SSE の同時接続枠を占有でき、`/api/state` の連打（毎回最大10万行を同期で導出）でイベントループを止められることが PoC で再現された（中）
- **原因**: no-cors のサブリソース GET（img・script・link など）では、ブラウザは Origin を付けない。Host はブラウザが正しい値を付けるので、Host 検査も素通りする。「Origin が無い＝ブラウザ以外（curl・フック）」とみなしていた
- **対処**: Host 検査の直後に「`Sec-Fetch-Site` があり、`same-origin` / `none` 以外なら 403」を入れた（ヘッダが無いクライアントは通す）。導出結果を `MAX(seq)` が変わったときだけ作り直すキャッシュを入れた
- **次回ルール**: ローカルの HTTP サーバでブラウザ経由の読み書きを塞ぐときは、Origin ではなく **`Sec-Fetch-Site` を一次判定**にする。Origin は補助。レスポンスを読めなくても**接続を張らせること自体**が攻撃になる（SSE の枠・重い GET）ので、読み出し系の GET も同じ検査に通す

### 2026-10-04 / #19 Issue に書いたコマンドを、起票時に一度も実行していなかった
- **事象**: #19 の受け入れ条件に「`node --test .claude/monitor/test/` を実行する」と書かれていた。Node 22.22 ではディレクトリ指定は Cannot find module で動かず、QA が glob（`*.test.mjs`）に変えた
- **原因**: Planner がコマンドの字面を推測で書き、手元で実行して確かめなかった（#6 と同じ構図）
- **対処**: glob で渡し、glob が空なら FAIL、件数の下限も検査するようにして、空振りで通らないようにした。PR に字面との差を明記した
- **次回ルール**: Issue の受け入れ条件にコマンドを書くときは、**起票時に手元で1回実行し、終了コードを確かめてから書く**。実行できない（未実装の対象を指す）なら、コマンドではなく「何が確認できればよいか」で書く

### 2026-10-04 / #18 G1 が CI の検査段を全部回していないと、全ゲート PASS でも CI が red になる

### 2026-10-04 / #18 差し戻しで挙動を変えたら、後続 Issue が契約に使う文書も同じ retry で直す

### 2026-09-30 / #18 外部コマンドは HOME 配下の設定ファイルを暗黙に読む。argv と env だけ塞いでも宛先は変わる
- **事象**: monitor-emit で宛先を `127.0.0.1` 固定にし、ホスト系・プロキシ系の環境変数を無視させた。G1〜G4 は PASS したが G5 が高で FAIL。curl は `-q` が無いと `.curlrc`（`CURL_HOME` / `XDG_CONFIG_HOME` / `HOME`）を読み、`url` で送信先を追加、`connect-to` で付け替え、`trace-ascii` でボディをファイルへ書き出せた。jq も `~/.jq` を自動で読み、組み込み関数（`test` / `with_entries` 等）を上書きされて allowlist を迂回された
- **原因**: 値の行き先と入口を「argv・環境変数・stdin・一時ファイル」で列挙し、**呼び出したツール自身が読む設定ファイル**を数えていなかった（#11 の列挙漏れの別形）
- **対処**: 未対処（ハードストップ中）。G5 の修正方針は curl の第1引数に `-q`、jq は `.jq` の無い `HOME` で起動、それぞれを設定ファイルで攻撃するテストと変異テストで固定
- **次回ルール**: フックやスクリプトから外部コマンドを呼ぶときは、**そのコマンドが暗黙に読む設定ファイル（rc・config・環境変数で場所が変わるもの）を列挙し、読ませない起動方法を先に決める**。curl は `-q` を第1引数、jq は `HOME` を差し替え、git は `GIT_CONFIG_NOSYSTEM` 等。テストは「設定ファイルを置いても挙動が変わらない」形で書く

### 2026-09-29 / #17 漏洩検査の禁止語は、記録の本文に字面で書くと検査に掛かる
- **事象**: `.claude/memory` の追跡 md を個人情報検査の対象に加えた直後、Benz がジャーナルに書いた「検査語の字面」の説明1行で G1 が FAIL した。epics の受け入れ条件の文にも同じ字面があり、誤検知した

- **対処**: 検査は緩めず、該当行を「`/Users`・`/home` 配下のパス」「ホーム配下を示す字面」のように末尾スラッシュ無しの表現へ言い換えた

- **事象**: Bash 経由の env ファイル操作を止めるガードを足し、security.md の見出しを「Bash からは触らせない」と書いた。G5 が中で FAIL。フックのコードは合格だったが、`grep -rn API_KEY .` / `cp -r` / `tar` のようなファイル名を書かない操作は通るのに、限界に書いていなかった
- **原因**: 実装の検知方式（コマンド中の名前）と、ドキュメントの主張（経路を塞いだ）の範囲が一致していなかった
- **対処**: 見出しを「名前で触るコマンドを止める」に弱め、限界に「ファイル名を書かない操作は検出しない」を追記。通過する経路を「既知の限界」としてテストで固定した
- **次回ルール**: ガードを足したら、**通ってしまう代表的な経路を1件、`assert_ok` の「既知の限界」テストとして書き、その経路を security.md の限界に書く**。書けない＝限界を把握していない
- **再発**: 2026-10-04 #20（security.md「コンテナ側」に、実行していないコマンドの結果を書いた。「イメージに wget を入れない」は busybox の wget が base にあり不正確。「`docker run -p` で全インターフェース公開」は MONITOR_BIND が compose にしか無く不正確。書き直した `docker run` の例も、実測で使った `-e MONITOR_DB` を書き漏らして起動失敗する手順になり、G2 が2連続 FAIL でハードストップ。**文書に載せるコマンド例は、文書に書いたとおりの文字列をそのまま実行して確かめる**。実測で足した引数を書き漏らすと、実測したことにならない）
