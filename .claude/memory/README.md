# メモリ層（ループの ＋1）

ループを構成する 5＋1 の部品のうち、**最も重要な「＋1」**がここ。

セッションの中だけで完結する記憶は、セッションが終われば消える。
それでは毎回「記憶喪失のジュニアエンジニア」を新規採用しているのと同じで、
何度でも同じ地雷を踏む。**セッションの外側に、状態と教訓を永続化する。**

---

## 構成

| パス | 内容 | Git |
| --- | --- | --- |
| `lessons.md` | 教訓。失敗と対処を言語化した資産（Reflection の出力） | **コミットする** |
| `journal/<epic-slug>.md` | 経緯。インナーループの節目ごとの記録（Vault へ書き写すまでの一時バッファ） | **コミットする** |
| `epics/<slug>.md` | 立案のメイド（Planner）が出したエピック分解結果 | **コミットする** |
| `loop-state.json` | 実行中のループ状態（retry 回数・ゲート結果・経過時間） | コミットしない |

`loop-state.json` は実行時の一時状態なので `.gitignore` 済み。
`lessons.md` はチームと未来のセッションの共有資産なので必ずコミットする。
`journal/` は**別端末・別作業者への引き継ぎ資産**なのでコミットする（端末固有のポインタ類のみ除外）。

### メモリは2層ある

```
外部（Obsidian Vault）  <VAULT>/projects/<project>.md   … 永続・追記のみ・リポジトリ外
        ↑ flush（アウターループ完了時に1回だけ）
内部（このディレクトリ） journal/<epic-slug>.md          … インナーの経緯。flush 後に削除
```

**なぜ外に出すのか。** リポジトリの中だけに記録を貯めると、リポジトリを跨いだ知見が育たない。
Vault にはプロジェクト横断で「何をやって、なぜそうしたか」が残る。

**なぜ内部に貯めるのか。** Vault はその端末のディスクにしか無い。
進行中のエピックの経緯は Git に乗せなければ、別のマシンで続きを拾えない。

実体は `.claude/scripts/loop-journal.sh`。運用の詳細は `journal/README.md`。

## 読み書きのタイミング

### 読む（必須）

**新しいタスクの最初の行動は、記録を読むこと。** コードに触れる前。

| いつ | 誰 | 何を |
| --- | --- | --- |
| **タスク開始時（最初の行動）** | メイド長（Benz） | `loop-journal.sh context` — 進行中なら内部ジャーナル、新規なら Vault |
| エピック分解時 | 立案のメイド（Planner） | `lessons.md` 全体 + Vault の直近エピック |
| Issue 開始時 | メイド長（Benz） | `lessons.md` のうち当該 Issue に関係する項目 |
| 実装開始時 | 構築のメイド（Coder） | Benz から渡された関連教訓と、前 Issue の設計判断 |

読む先の判定:

| 状況 | 読む先 |
| --- | --- |
| 新規アウターループの最初のインナータスク | 外部 Vault `projects/<project>.md` |
| 進行中のアウターループの中間タスク | 内部ジャーナル `journal/<epic-slug>.md` |

### 書く（必須）

| いつ | 誰 | 何を |
| --- | --- | --- |
| インナーの節目4点 | メイド長（Benz） | `journal/<epic>.md`（`loop-journal.sh inner`） |
| アウターの節目 | メイド長（Benz） | Vault へ直接（`loop-journal.sh outer`） |
| ゲート FAIL 時 | 各ゲート担当 | `loop-state.json`（`loop-state.sh gate` 経由） |
| Issue 完了時 | メイド長（Benz） | `lessons.md` に Reflection を追記（`/loop-retro`） |
| ハードストップ時 | メイド長（Benz） | `lessons.md` に「解決できなかった事実」を追記 + ジャーナルに `halt` |
| **エピック完了時** | メイド長（Benz） | `loop-journal.sh flush` で内部ジャーナルを Vault へ書き写して削除 |

インナーの節目は4点だけ。ゲート1つごとには書かない:
`start`（着手）/ `impl`（実装完了）/ `gates`（ゲート一巡）/ `done` または `halt`（完了・停止）

## 教訓の書き方

**「気をつける」は教訓ではない。** 次のセッションの AI が読んで**行動を変えられる粒度**で書く。

悪い例:
```md
- 型エラーに注意する
```

良い例:
```md
### 2026-09-01 / #42 記事検索
- **事象**: Server Action の戻り値を直接 `useQuery` に渡して型が `any` に落ちた
- **原因**: Server Action の戻り値型を Zod スキーマから導出していなかった
- **対処**: `types/article.ts` に `SearchResultSchema` を定義し `z.infer` で受ける
- **次回ルール**: Server Action の戻り値は必ず Zod スキーマとペアで定義する
```

**`次回ルール` が最重要。** そこだけ読めば次の実装が変わる、という一行にする。

---

## 運用ルール

- **成功だけを書かない**: 失敗こそ資産。ハードストップに至った案件は必ず記録する
- **重複させない**: 同じ教訓が既にある場合は、新規追加せず既存項目に日付と事例を追記する
- **肥大化させない**: 30項目を超えたらカテゴリ別に整理し、陳腐化した教訓は削除する
- **憶測を書かない**: 「たぶんこれが原因」は書かない。確認できた事実と、確認できていないことを分けて書く
- **プロジェクト固有にする**: 一般論（「テストは大事」）は書かない。このコードベースでしか通用しない知識だけを書く
- **教訓と経緯を混ぜない**: 次回ルールは `lessons.md`、「なぜそう実装したか」は `journal/`。
  ジャーナルはエピック完了で消えるので、教訓をそこに書くと教訓ごと消える
- **未フラッシュのジャーナルを手で消さない**: 中身はまだ Vault に無い。消せば経緯は完全に失われる
