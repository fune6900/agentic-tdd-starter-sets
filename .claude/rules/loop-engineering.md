# ループエンジニアリング

**設計対象は「指示」ではない。「AI が AI に指示を出し続ける仕組み」そのものだ。**

このファイルはループ設計の憲法。`dev-flow.md` が「1イシューをどう作るか」を規定するのに対し、
このファイルは「ループをどう回し、どこで止めるか」を規定する。

---

## 設計概念の位置づけ

```
プロンプトエンジニアリング  … 1回の指示文の質を上げる
        ↓ 内包
コンテキストエンジニアリング … 背景情報を丸ごと渡す
        ↓ 内包
ハーネスエンジニアリング   … ルール・制約・検証（走行路とガードレール）を設計する
        ↓ 内包
ループエンジニアリング     … AI が自律的に回り続ける組織構造とワークフローを設計する
```

新しい層は古い層を捨てない。**内包して上に積む**。
このリポジトリの `.claude/rules/` 全体がハーネス層であり、その上にループ層を載せる。

---

## 前提: AI は「粘り強いジュニアエンジニアのチーム」

天才ではない。放置すれば迷い、暴走し、トークンを燃やす。
だからループ設計者（マスター／Benz）の仕事は、以下4条件を満たす環境を用意することに尽きる。

| # | 条件 | このリポジトリでの実体 |
| --- | --- | --- |
| ① | **明確なタスク定義** | 立案のメイド（Planner）が生成する Issue。ゴールを一行で言い切る |
| ② | **安全な作業環境** | git worktree による作業領域分離（`.claude/scripts/worktree.sh`） |
| ③ | **機械的な成功判定** | test / typecheck / lint / build と多軸レビューのゲート |
| ④ | **ハードストップ** | リトライ上限・時間上限・行き詰まり時の人間へのエスカレーション |

**④が無いループは設計ではない。事故だ。**

## 2層構造

### インナーループ（1タスク内）

1つの Issue の中で「実装 → 検証 → 差し戻し」を人間を介さず回す。
実体は `/issue-flow`。

```
    ┌──────────────────────────────────────────────┐
    │  Issue 1本                                   │
    │                                              │
    │  実装（Architect → Coder → Designer）         │
    │        ↓                                     │
    │  G1 機械ゲート    Evaluator                   │
    │  G2 実証ゲート    実証のメイド（Playwright）    │
    │  G3 仕様ゲート    照合のメイド                 │
    │  G4 コードゲート  校閲のメイド                 │
    │  G5 セキュリティ  守衛のメイド（条件起動）       │
    │        ↓ 1つでも FAIL                        │
    │  差し戻し → 実装へ（retry++）                  │
    │        ↓ 全ゲート PASS                        │
    │  PR 作成 → Issue 完了                         │
    │                                              │
    │  retry が上限到達 → ハードストップ → 人間へ報告 │
    └──────────────────────────────────────────────┘
```

ReAct（思考 → 行動 → 観測）の実装形態。
「AI がやりましたと言ったが実は壊れている」を、**AI が AI を検証する**ことで潰す。

### アウターループ（複数タスク横断）

エピック（大きな要件）を Issue に分解し、順に流し、**セッションを跨いで学習する**。
実体は `/epic-flow`。

```
    ┌────────────────────────────────────────────────┐
    │  Epic 1本                                      │
    │                                                │
    │  立案のメイド（Planner）が Issue に分解          │
    │        ↓                                       │
    │  人間が承認（★ここだけ人間が必須）               │
    │        ↓                                       │
    │  Issue #1 → /issue-flow（インナーループ）        │
    │        ↓ 完了時に Reflection を memory へ書く    │
    │  Issue #2 → /issue-flow（前回の教訓を読んで開始） │
    │        ↓                                       │
    │  …全 Issue 完了 → epic ブランチで統合 PR         │
    │        ↓                                       │
    │  人間が最終確認                                  │
    └────────────────────────────────────────────────┘
```

アウターループの価値は**メモリ**にある。
前の Issue で踏んだ地雷を `.claude/memory/lessons.md` に言語化して記録し、
次の Issue の開始時に読ませる。これが Reflection であり、同じミスを繰り返さない唯一の手段。

## ループを構成する 5＋1 の部品

Addy Osmani のフレームワークと、このリポジトリの実装の対応表。

| # | 部品 | 役割 | 実体 |
| --- | --- | --- | --- |
| ① | 自動化（Automation） | 定期的にタスクを発見しエージェントを起動する | `.github/workflows/loop-automation.yml` |
| ② | ワークツリー（Worktree） | 作業領域を分離し衝突を防ぐ | `.claude/scripts/worktree.sh` / `/worktree` |
| ③ | スキル（Skills） | 成果を確定・永続化させるハーネス | `.claude/rules/` 全体 + `.claude/hooks/` |
| ④ | プラグイン / コネクター | 外部世界（GitHub, ブラウザ, docs）との接続 | `gh` CLI, Playwright MCP, Chrome DevTools MCP, Context7 MCP |
| ⑤ | サブエージェント | 「作る役」と「検証する役」の分業 | `.claude/agents/` 11体 |
| ＋1 | **メモリ（Memory）** | セッション外に状態と教訓を永続化する | `.claude/memory/` |

**メモリが最重要**。①〜⑤が揃っていてもメモリが無いループは、
毎回記憶喪失のジュニアを新規採用しているのと同じで、永久に学習しない。

## ゲート定義

インナーループの合格判定は以下で機械的に決まる。主観は挟まない。

| ゲート | 担当 | 判定基準 | 起動条件 |
| --- | --- | --- | --- |
| **G1 機械** | 評価のメイド（Evaluator） | `npm test -- --run` / `typecheck` / `lint` / `build` が全て成功 | 常時 |
| **G2 実証** | 実証のメイド（Tester） | 受け入れ条件を実画面（Playwright）で満たす | 常時（UI 無し変更ではコマンド実行確認で代替） |
| **G3 仕様** | 照合のメイド（Spec Reviewer） | Issue の目的・意図に対する充足、影響範囲の逸脱なし | 常時 |
| **G4 コード** | 校閲のメイド（Code Reviewer） | 可読性・重複・命名・規約。重要度「高」の指摘ゼロ | 常時 |
| **G5 セキュリティ** | 守衛のメイド（Security Reviewer） | `security.md` の全項目を充足 | **条件起動**（下記） |

### G5 の条件起動

セキュリティレビューは常時起動しない。コスト（Opus）に見合う場合のみ立ち上げる。
以下のいずれかに該当する変更で**必須**、それ以外は Planner が Issue 作成時に要否を明記する。

- 認証・認可・セッション・Cookie に触れる
- 外部入力を受け取る境界（Server Action / Route Handler / Webhook / フォーム）を追加・変更する
- SQL・ORM クエリ・生SQL を追加・変更する
- 環境変数・シークレット・外部 API キーを扱う
- `dangerouslySetInnerHTML` / `eval` / 動的インポートを含む
- 依存パッケージを追加する

## ハードストップ（必須）

「合格するまでやり直せ」とだけ命じるのは設計放棄。解けない問題に無限リトライしてコストが死ぬ。

### 停止条件

| 種別 | 既定値 | 環境変数 |
| --- | --- | --- |
| 最大リトライ回数（1 Issue あたり） | **3** | `LOOP_MAX_RETRY` |
| 最大経過時間（1 Issue あたり・分） | **60** | `LOOP_MAX_MINUTES` |
| 同一ゲートの連続 FAIL | **2** | `LOOP_MAX_SAME_GATE_FAIL` |

### 停止時の挙動

上限に到達したら、**勝手に進むな。勝手に止まるな。人間に報告して指示を仰げ。**

1. `.claude/scripts/loop-state.sh stop "<理由>"` で状態を `halted` にする
2. 以下を必ず報告する
   - 何回目のリトライで、どのゲートで、何が落ちたか
   - 各リトライで何を変えたか（同じ修正を繰り返していないか）
   - 現時点の推定原因と、人間に判断を求めたい選択肢
3. `.claude/memory/lessons.md` に「解決できなかった事実」として記録する
4. **コミットも PR 作成もしない。** 中途半端な成果物を main に近づけない

### 禁止事項

- ゲートを通すためにテストを削除・スキップ・`.skip` 化する
- `--no-verify` でフックを回避する
- 「たぶん直った」で次のゲートに進む
- ハードストップに達したのに黙って別のアプローチを試し続ける

## メモリ・プロトコル

### 書き込み先

| ファイル | 内容 | Git |
| --- | --- | --- |
| `.claude/memory/lessons.md` | 教訓（失敗と対処の言語化）。セッションを跨いで永続 | **コミットする** |
| `.claude/memory/loop-state.json` | 実行中の状態（retry 回数・ゲート結果・開始時刻） | コミットしない（`.gitignore`） |

### 読み込みタイミング

- **Issue 開始時（必須）**: `lessons.md` を読み、当該 Issue に関係する教訓を実装方針に反映する
- **Planner の分解時（必須）**: 過去の教訓を踏まえて受け入れ条件を設計する

### 書き込みタイミング

- **ゲート FAIL 時**: 何が落ちたかを `loop-state.json` に記録
- **Issue 完了時 / ハードストップ時（必須）**: `/loop-retro` で `lessons.md` に追記

### 教訓の書き方

「気をつける」は教訓ではない。**次のセッションの AI が読んで行動を変えられる粒度**で書く。

```md
### 2026-09-01 / #42 記事検索
- **事象**: Server Action の戻り値を直接 `useQuery` に渡して型が `any` に落ちた
- **原因**: Server Action の戻り値型を Zod スキーマから導出していなかった
- **対処**: `types/article.ts` に `SearchResultSchema` を定義し `z.infer` で受ける
- **次回ルール**: Server Action の戻り値は必ず Zod スキーマとペアで定義する
```

## 人間が介在する場所

ループエンジニアリングでも人間はゼロにならない。**介在する場所を固定する**のが設計。

| タイミング | 人間の役割 | 必須か |
| --- | --- | --- |
| エピックの要件定義 | ゴールを決める | **必須** |
| Planner の分解結果の承認 | Issue 分割・受け入れ条件を承認する | **必須** |
| インナーループ実行中 | **介在しない** | — |
| ハードストップ発動時 | 原因判断・方針指示 | **必須** |
| エピック統合 PR の最終確認 | マージ判断 | **必須** |

インナーループの途中で人間が覗き込むのは、設計ではなく不安。ゲートを信じるか、ゲートを直せ。
